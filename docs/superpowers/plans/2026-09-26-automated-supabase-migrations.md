# Automated Supabase Migrations: Setup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Set up the pipeline that applies `supabase/migrations/*` to production Supabase on push to `main`. It ships **disabled**. Production is not touched by this plan.

**Architecture:**
- The existing migrations move into a Supabase CLI project folder, `supabase/`, at the repo root.
- A GitHub Actions workflow runs `supabase db push` on `main`, and `--dry-run` on pull requests.
- The whole job is gated on the repository variable `SUPABASE_MIGRATIONS_ENABLED`. The user sets it to `true` only after doing the one-time production baseline, which is documented in `supabase/README.md`.
- The sandbox branch is then rebased onto the new layout.

**Tech Stack:** Supabase CLI 2.109.0, GitHub Actions (`supabase/setup-cli@v1`), bash (`sandbox/sandbox.sh`), Docker (`postgres:15-alpine` as a throwaway test database).

**Spec:** `docs/superpowers/specs/2026-09-26-automated-supabase-migrations-design.md`

## Scope change from the spec (user, 2026-09-26)

"We just need to set it up." So:
- **Not in this plan:** the spec's Verification steps 2–4 (the production `migration repair`, the production dry-run, and the first real run that applies 011). They become a checklist in `supabase/README.md` for the user to do later.
- **Added to this plan:** the `SUPABASE_MIGRATIONS_ENABLED` gate. Without it, the first push to `main` would run every migration (001–011) against production, which has no history table, and 010 would replace production's functions.

## Global Constraints

- **Pin the CLI:** `supabase/setup-cli@v1` with `version: 2.109.0`, never `latest`.
- **Production project ref:** `rhtbqqprloedsvvdvxak` (NJ-Dot 2.0).
- **Secret names:** `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `SUPABASE_PROJECT_ID`. The user adds them; Claude never handles their values.

- **Migration versions:** 001 → `20260101000001`, 002 → `20260101000002`, 009 → `20260101000009`, 010 → `20260101000010`, 011 → `20260101000011`.
- **No production writes in this plan.** No `repair`, no `db push` against `--linked`, and no setting the enable variable.
- **Pushing branches to GitHub** happens only after the user says so in chat.
- **Commits end with:** `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A manual "Run workflow" from a non-`main` branch must never apply**, only dry-run. Pinned by `test_apply_only_on_main` (Task 2).
2. **Before the gate is enabled, pushes to `main` must skip the job, not fail and not apply.** Pinned by `test_job_gated_on_variable` (Task 2).
3. **The move must not change any migration's content**, because production's objects came from these exact files. Pinned by Task 1 Step 4, which requires every rename to be 100% similar.

5. **The sandbox's `db-apply` still applies 011 and can be re-run.** Pinned by Task 4 Step 5 (run twice, both succeed, `conversations_delete` exists).

- [ ] **Step 2: Write the workflow.**

  ```yaml
  # Applies supabase/migrations/* to production Supabase (NJ-Dot 2.0) on push
  # to main; pull requests get a dry run listing what would be applied.
  # Design: docs/superpowers/specs/2026-09-26-automated-supabase-migrations-design.md
  #
  # SHIPS DISABLED. The job is skipped until the repository variable
  # SUPABASE_MIGRATIONS_ENABLED is "true". Do the one-time production
  # baseline in supabase/README.md FIRST: without it, the first run would
  # re-apply every migration to production (which has no history table).
  #
  # Repository secrets (Settings -> Secrets and variables -> Actions):
  #   SUPABASE_ACCESS_TOKEN  personal access token (supabase.com/dashboard/account/tokens)
  #   SUPABASE_DB_PASSWORD   NJ-Dot 2.0 database password
  #   SUPABASE_PROJECT_ID    rhtbqqprloedsvvdvxak

  name: Supabase migrations

  on:
    push:
      branches: [main]
      paths:
        - 'supabase/migrations/**'
        - '.github/workflows/supabase-migrations.yml'
    pull_request:
      paths:
        - 'supabase/migrations/**'
        - '.github/workflows/supabase-migrations.yml'
    workflow_dispatch: {}

  # One migration run at a time; a second push waits instead of racing.
  concurrency:
    group: supabase-migrations-production
    cancel-in-progress: false

  jobs:
    migrate:
      if: vars.SUPABASE_MIGRATIONS_ENABLED == 'true'
      runs-on: ubuntu-latest
      env:
        SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
        SUPABASE_DB_PASSWORD: ${{ secrets.SUPABASE_DB_PASSWORD }}
        SUPABASE_PROJECT_ID: ${{ secrets.SUPABASE_PROJECT_ID }}
      steps:
        - uses: actions/checkout@v6

        - uses: supabase/setup-cli@v1
          with:
            version: 2.109.0

        - run: supabase link --project-ref "$SUPABASE_PROJECT_ID"

        # Pull requests and manual runs from other branches only preview.
        - name: Preview pending migrations
          if: github.ref != 'refs/heads/main'
          run: supabase db push --dry-run

        # Each migration file is atomic: a failure rolls that file back and
        # records nothing, so fix it with a new commit and push again.
        - name: Apply pending migrations
          if: github.ref == 'refs/heads/main'
          run: supabase db push --yes
  ```

### Task 3: Rules and the enablement checklist

**Files:**
- Create: `supabase/README.md`

- [ ] **Step 1: Write `supabase/README.md`.**

  ````markdown
  # Database migrations

  Every schema change to production Supabase (NJ-Dot 2.0) ships as a file in
  `supabase/migrations/`. `.github/workflows/supabase-migrations.yml`
  applies new files on push to `main`; pull requests get a dry run.

  ## Writing a migration

  1. `supabase migration new <short_name>`. Never invent the filename.
  2. One logical change per file. Each file runs in one transaction: if it
     fails, it is rolled back and not recorded, so fix it and push again.
  3. **Additive only.** The backend (Azure) and migrations deploy in parallel,
     so either may land first. Add columns, tables and policies. To drop or
     rename something, first ship code that no longer uses it, then the
     migration.
  4. Guard statements where cheap: `if not exists`, guarded `create policy`.
  5. Never edit a migration once it is on `main`; add a new one. `db push`
     refuses to run if production's history and these files disagree.
  6. Preview before merging: `supabase db push --dry-run --linked`, or read
     the dry-run output on the pull request.

  ## Turning the pipeline on (one time)

  The workflow ships disabled. Its job is skipped until the repository
  variable `SUPABASE_MIGRATIONS_ENABLED` is `true`. Before production had
  this pipeline, migrations 001, 002, 009 and 010 were applied by hand,
  and 011 was not (checked 2026-09-26).

  1. Add these repository secrets (Settings → Secrets and variables → Actions):
     - `SUPABASE_ACCESS_TOKEN`
     - `SUPABASE_DB_PASSWORD`
     - `SUPABASE_PROJECT_ID` = `rhtbqqprloedsvvdvxak`
  2. Link locally, from the repo root:
     `supabase link --project-ref rhtbqqprloedsvvdvxak`
  3. Baseline. This marks the migrations production already has, without
     running them, and creates the history table:

     ```bash
     supabase migration repair --status applied 20260101000001 20260101000002 20260101000009 20260101000010 --linked
     ```

  4. Check that `supabase db push --dry-run --linked` lists **only**
     `20260101000011_conversations_update_delete_policies.sql`.
  5. Set the repository variable `SUPABASE_MIGRATIONS_ENABLED` = `true`
     (Settings → Secrets and variables → Actions → Variables).
  6. Run the workflow from the Actions tab on `main`, or merge the next
     migration. It applies 011. Confirm with `supabase migration list --linked`,
     which should show all five versions on both sides.
  ````
